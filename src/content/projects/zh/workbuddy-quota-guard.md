在 WorkBuddy 里跑复杂任务时，最让人窝火的一幕是：任务跑到一半，模型直接返回 **429**，一切被硬生生打断；而客户端界面上根本看不到「这个模型我还剩多少额度」，只能等撞墙才知道。

被限流 → 换模型 → 重跑 → 质量不可控 + 大量重复劳动。这套循环，我自己走过太多次。

## 要解决什么

问题不在于「余额不够」，而在于**限额是「账号 × 模型」粒度的独立配额，且按滚动 24 小时窗口重置**：

- 客户端只暴露总额度，不暴露每个模型的剩余量；
- CLI 层不返回任何 `rate-limit` 响应头；
- 没有信号，就没有「提前规划」和「平滑换模型」的依据。

所以在撞墙之前，人是完全没有预警的。

## 怎么做的

核心思路是：**只读解析本地会话日志，反推每个模型的历史限额，用同一套窗口语义估算当前剩余量。**

关键在两个技术点：

| 问题 | 解法 |
| ---- | ---- |
| 不知道每个模型的限额是多少 | 扫描日志抽取所有 429 事件及其携带的窗口重置时刻，对每个模型取该次窗口内**仅该模型自身**的消耗，多样本取中位数 → 限额**下界估计** |
| 429 事件本身不带模型字段 | 会话邻近法归因：取同会话内、该 429 之前 120 秒内最近一次成功请求所用的模型，找不到时回退会话内多数模型 |

窗口语义是这里最容易出错的地方：实测相邻两次 reset 的间隔中位数为 **24.01 小时**，说明限额走的是**滚动窗口**而非自然日。于是当前状态统一按 `(now - W, now]` 统计，与反推时的口径严格一致。

> 为什么是「下界」：被限流说明**至少**已消耗到超限，所以样本值只会低估真实限额。

## 现在的能力

一套只读、零依赖（纯 Python 标准库）的工具，覆盖从预警到交接的完整链路：

- **限额反推**：输出 `limits.json`，含全局阈值、每模型限额与错误码统计；
- **实时状态**：按当前滚动窗口估算各模型已用占比与风险等级（low / medium / high）；
- **可视化看板**：自适应暗色 HTML，浏览器直接打开；
- **断点交接**：一键生成五段式 `handoff.md`，429 中断时直接交给下一个模型接手；
- **Hook 预警**：注册到 `SessionStart` 事件，会话一开始就检查额度并提示高风险模型；
- **Skill 化**：可作为 WorkBuddy Skill 安装，用一句自然语言调用。

实测样例中，`hy4-preview` 在滚动窗口内的用量占比达到 **1.748**（风险 high），`deepseek-v4.1-flash` 为 **1.097**（high）—— 这两个数字，在撞上 429 之前本来是完全看不见的。

## 已知边界

工具的能力边界写得比功能更重要，因为它是反推出来的：

| 限制 | 说明 |
| ---- | ---- |
| 限额是统计下界 | 样本少的模型可信度低，需实际触发后校准 |
| 拿不到真实剩余额度 | 客户端登录态存于 Electron DPAPI 加密存储，外部脚本读不到，只能从日志反推 |
| 依赖本地日志 | 清空会话日志会丢失历史样本，需重新积累 |
| 平台相关 | 目前针对 WorkBuddy / CodeBuddy 桌面客户端 |

## 隐私与安全

- **只读**访问本地日志，不修改、不删除任何 WorkBuddy 数据；
- 不上传任何数据到网络；
- 生成的产物默认在 `.gitignore` 中，不入库；
- 仓库内不含任何个人标识、账号 ID 与会话内容。
