# 文章润色与排版规范（SOP）

> 背景：Markdown 本身只描述结构、不负责美观。站点已做两件事——**升级 `.prose` 渲染样式**（CSS）+ **逐篇润色内容结构**（本文规范）。
> 二者的分工：CSS 解决「渲染好不好看」，润色解决「结构清不清楚」。只做前者不够，只做后者也不够。

---

## 一、站点已支持的增强渲染（写文时直接用这些语法）

| Markdown 语法 | 渲染效果 | 使用建议 |
| ------------- | -------- | -------- |
| `## 二级标题` | 上方带细分隔线的大标题，块间距 48px | 全文分 3–6 节，每节一个 |
| `### 三级标题` | 20px 加粗小标题 | 一节内再分层时使用，不要连续堆 |
| `> 引用` | **卡片化**（浅灰底 + 蓝色左侧条），不再是斜体 | 放「一句话结论」或关键判断，一节最多 1 个 |
| `**加粗**` | 纯黑加粗 | 中文强调**用加粗**，不用斜体（中文斜体是合成字形，难看） |
| `*斜体*` | 灰色、不倾斜 | **仅用于图注**（见下条）与外文原文 |
| `![图](url)` 独占一段 | 圆角 + 阴影 | 图必须独占一段，否则图注规则失效 |
| 图片段后紧跟 `*说明文字*` | 自动渲染为**居中灰色小字图注** | 这是本站的图注约定 |
| 表格 | 浅灰表头 + 圆角边框 + 偶数行浅底 | 对比类信息优先用表格，别写成一大段 |
| `- [ ]` / `- [x]` | 任务列表（复选框，无圆点） | 清单、步骤、待办 |
| `1. 2. 3.` | 有序列表，序号加粗灰色 | 有先后/因果关系的步骤 |
| ``` 代码块 ``` | 深色块 + 圆角 + 阴影 + 横向滚动 | 展示命令、配置、代码片段 |
| `---` | 细分隔线 | 大节之间转场，勿滥用 |
| `> [!tip]` 等 callout | 彩色提示框（tip/note/warning/important/danger） | 从知识库导入的实践类内容会用 |

> ⚠️ 注意：图注靠 CSS `:has()` 实现，**必须是「图片独占一段」+「下一段只有一句斜体」**才生效。老浏览器不生效时退化为普通斜体，不影响阅读。

## 二、Frontmatter 规范

```markdown
---
title: 标题（12 字以内最佳，列表页与详情页都显示）
lang: zh
date: 2026-09-27
summary: 一句话摘要（40–60 字）— 显示在卡片上，是点击率的关键
tags: [标签1, 标签2]        # 2–4 个，跨文章保持一致（如：AI工程、工具开发、产品思考）
cover: /cover-xxx.png       # 可选，放 public/ 下
draft: false                # true = 不上线
---
```

- `summary` **不要**复制首段，要写成「读完能带走什么」
- `tags` 先想好词表再写，避免「AI / ai / 人工智能」三种写法并存

## 三、结构规范（润色的核心）

### 3.1 开篇（最重要）

- 第一段（自动放大 1 号字）必须**直接给结论或抛出问题**，不要寒暄、不要「随着…的发展」
- 长度控制在 2–4 句。写完问自己：读者看完这一段，知道这篇要讲什么吗？

### 3.2 正文分层

- 每节一个 `##`，标题是**结论短语**（如「先算缓存命中率」），不是名词（如「缓存」）
- 段落 **3–5 句一段**，超过 6 句就拆；移动端一大坨文字会劝退
- 一节内连续 3 段以上纯文字，就要插入列表 / 引用 / 表格 / 图 之一

### 3.3 收尾

- 结尾回到开篇的承诺：给结论、给下一步、或给一个留白判断
- 避免「以上就是我的分享」这类空话

### 3.4 语言层面

| 项 | 要求 |
| -- | ---- |
| 中英混排 | 中英文之间加空格：`用 Astro 构建`（不是 `用Astro构建`） |
| 术语 | 首次出现给全称 + 缩写，后续用缩写 |
| 长句 | 单句不超过 40 字，超了用句号拆 |
| 数字 | 用阿拉伯数字；带单位写 `58.52s` 不写 `58.52 秒`（代码/技术文） |
| 口语 | 允许口语化，但删掉口头禅与重复强调 |

## 四、润色检查清单（每篇过一遍）

```
结构
□ 开篇 2–4 句，直接给结论/问题，无寒暄
□ 全文 3–6 个 ## 分节，标题是结论短语
□ 每段 ≤ 5 句；无视觉上的「文字墙」
□ 结尾回到开篇，有明确结论或行动项
□ 连续纯文字段不超过 3 段

表达
□ 强调统一用 **加粗**，无滥用斜体
□ 中英文之间有空格
□ 单句 ≤ 40 字
□ 无口头禅、无重复表述
□ 术语首次出现有解释

排版元素
□ 对比/并列信息用表格或列表，而非长段落
□ 关键判断用 > 引用卡片（每节 ≤ 1 个）
□ 图片独占一段 + 紧跟斜体图注
□ 代码/命令用代码块
□ 步骤类用有序列表，清单类用无序/任务列表

元数据
□ title 简洁（≤12 字）
□ summary 写「读完能带走什么」，40–60 字
□ tags 复用既有词表，2–4 个
□ date 正确，draft: false
□ 无外链失效（如有链接逐个点开验证）

终检
□ 本地 npm run build 通过
□ 详情页首屏无明显排版异常
□ 移动端（窄屏）标题不溢出
```

## 五、润色前后对照（示例）

**润色前**

```
随着 AI 编程工具的普及，token 消耗成了一个不可忽视的问题。我在使用 WorkBuddy 的过程中发现，UI 上只能看到额度，看不到明细，这就导致无法进行成本归因。为了解决这个问题，我开发了一个工具，它可以解析本地日志，然后按任务维度统计 token 消耗，并且支持分档计价。实测发现缓存命中率很高，如果按通用两档计价会高估成本。
```

**润色后**

```
用 AI 干活久了，最说不清的一个问题是：**这笔活到底烧了多少 token、值多少钱**。UI 上只能看到额度，看不到明细，更没法按任务归因。

我做了一个工具来回答它：解析本地请求日志，按任务维度核算消耗，并按真实档位计价。

## 关键发现

实测下来，本机的缓存命中率超过 95%。

| 计价方式 | 结果 |
| -------- | ---- |
| 通用输入/输出两档 | 高估约 70% |
| 分档（非缓存/命中/写入） | 接近真实 |

> 分档计价不是优化项，而是准确性的前提。
```

> 差别不在字数，而在**信息分层**：结论前置、长段拆开、数字进表格、判断进引用。

## 六、发布流程

1. **选文**：你指定本地 md 文件路径（或直接把内容贴给我）
2. **润色**：我按第三节结构规范 + 第四节清单改写，`summary`/`tags` 一并定
3. **入库**：写入 `src/content/articles/zh/<slug>.md`（slug 用英文小写连字符）
4. **验证**：`npm run build` 通过
5. **提交**：你用 GitHub Desktop 提交推送，Netlify 自动上线

> 本轮只出中文版（`lang: zh`）。英文版后续补：在同目录建 `en/<slug>.md`，详情页的语言切换按钮会自动出现。
