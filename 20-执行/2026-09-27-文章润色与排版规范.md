# 文章润色与排版规范（SOP）

> 背景：Markdown 本身只描述结构、不负责美观。站点已做两件事——**升级 `.prose` 渲染样式**（CSS）+ **逐篇润色内容结构**（本文规范）。
> 二者的分工：CSS 解决「渲染好不好看」，润色解决「结构清不清楚」。只做前者不够，只做后者也不够。
>
> **配套文档**：内容字段、增改流程、校验与推送门禁见 [[项目/个人网站编写测试/20-执行/2026-09-30-内容增改管理规范]]（总纲）；本文只管排版与阅读体验。
>
> **2026-09-30 更新**：修正 callout 转译的失准描述；新增第七节 SVG 图表规范、第八节项目栏目排版、第九节推送前验证、第十节图表选型。

## 一、站点已支持的增强渲染（写文时直接用这些语法）

| Markdown 语法 | 渲染效果 | 使用建议 |
| ------------- | -------- | -------- |
| `## 二级标题` | 上方带细分隔线的大标题，块间距 48px | 全文分 3–6 节，每节一个 |
| `### 三级标题` | 20px 加粗小标题 | 一节内再分层时使用，不要连续堆 |
| `> 引用` | **卡片化**（浅灰底 + 蓝色左侧条），不再是斜体 | 放「一句话结论」或关键判断，一节最多 1 个 |
| `**加粗**` | 纯黑加粗 | 中文强调**用加粗**，不用斜体（中文斜体是合成字形，难看） |
| `*斜体*` | 灰色、不倾斜 | **仅用于图注**（见下条）与外文原文 |
| `![图](url)` 独占一段 | 圆角 + 阴影 | 图必须独占一段，否则图注规则失效 |
| 图片段后紧跟 `*说明文字*` | 自动渲染为**居中灰色小字图注** | 这是本站的图注约定 |
| 表格 | 浅灰表头 + 圆角边框 + 偶数行浅底 | 对比类信息优先用表格，别写成一大段 |
| `- [ ]` / `- [x]` | 任务列表（复选框，无圆点） | 清单、步骤、待办 |
| `1. 2. 3.` | 有序列表，序号加粗灰色 | 有先后/因果关系的步骤 |
| ``` 代码块 ``` | 深色块 + 圆角 + 阴影 + 横向滚动 | 展示命令、配置、代码片段 |
| `---` | 细分隔线 | 大节之间转场，勿滥用 |
| `<div class="callout callout-tip">` | 彩色提示框 | **手写文章见下方 ⚠️ 说明** |

> ⚠️ **Callout 的正确用法（2026-09-30 修正）**
>
> 站点的 `> [!tip]` → 彩色提示框转译，**只存在于 `scripts/import-practice.mjs`**（知识库导入链路）。**手写 md 不经过该脚本，写了会原样残留成字面文本**——构建不报错，只有打开页面才看得到。
>
> 手写文章请直接用 HTML 形式：
>
> ```html
> <div class="callout callout-tip">
> <p class="callout-title">标题文字</p>
> <p>正文内容，可含 <strong>加粗</strong> 与 <code>代码</code>。</p>
> </div>
> ```
>
> **可用的类型**（对应 `global.css` 已有样式，勿自造）：
>
> | 类名 | 配色 | 适用 |
> | ---- | ---- | ---- |
> | `callout-tip` | 绿 | 经验、可复用结论 |
> | `callout-warning` | 橙 | 踩坑、风险提示 |
> | `callout-important` | 蓝 | 必须遵守的约定 |
> | `callout-note` | 灰 | 补充说明 |
> | `callout-danger` | 红 | 严重错误 |
>
> 自造颜色或自写 `style="..."` 内联样式会导致视觉与站点不一致。

> ⚠️ 注意：图注靠 CSS `:has()` 实现，**必须是「图片独占一段」+「下一段只有一句斜体」**才生效。老浏览器不生效时退化为普通斜体，不影响阅读。

## 二、Frontmatter 规范

```markdown
---
title: 标题（12 字以内最佳，列表页与详情页都显示）
lang: zh
date: 2026-09-27
summary: 一句话摘要（40–60 字）— 显示在卡片上，是点击率的关键
tags: [标签1, 标签2]        # 2–4 个，跨文章保持一致（如：AI工程、工具开发、产品思考）
cover: /cover-xxx.png       # 可选，放 public/ 下
draft: false                # true = 不上线
---
```

- `summary` **不要**复制首段，要写成「读完能带走什么」
- `tags` 先想好词表再写，避免「AI / ai / 人工智能」三种写法并存

## 三、结构规范（润色的核心）

### 3.1 开篇（最重要）

- 第一段（自动放大 1 号字）必须**直接给结论或抛出问题**，不要寒暄、不要「随着…的发展」
- 长度控制在 2–4 句。写完问自己：读者看完这一段，知道这篇要讲什么吗？

### 3.2 正文分层

- 每节一个 `##`，标题是**结论短语**（如「先算缓存命中率」），不是名词（如「缓存」）
- 段落 **3–5 句一段**，超过 6 句就拆；移动端一大坨文字会劝退
- 一节内连续 3 段以上纯文字，就要插入列表 / 引用 / 表格 / 图 之一

### 3.3 收尾

- 结尾回到开篇的承诺：给结论、给下一步、或给一个留白判断
- 避免「以上就是我的分享」这类空话

### 3.4 语言层面

| 项 | 要求 |
| -- | ---- |
| 中英混排 | 中英文之间加空格：`用 Astro 构建`（不是 `用Astro构建`） |
| 术语 | 首次出现给全称 + 缩写，后续用缩写 |
| 长句 | 单句不超过 40 字，超了用句号拆 |
| 数字 | 用阿拉伯数字；带单位写 `58.52s` 不写 `58.52 秒`（代码/技术文） |
| 口语 | 允许口语化，但删掉口头禅与重复强调 |

## 四、润色检查清单（每篇过一遍）

```
结构
□ 开篇 2–4 句，直接给结论/问题，无寒暄
□ 全文 3–6 个 ## 分节，标题是结论短语
□ 每段 ≤ 5 句；无视觉上的「文字墙」
□ 结尾回到开篇，有明确结论或行动项
□ 连续纯文字段不超过 3 段

表达
□ 强调统一用 **加粗**，无滥用斜体
□ 中英文之间有空格
□ 单句 ≤ 40 字
□ 无口头禅、无重复表述
□ 术语首次出现有解释

排版元素
□ 对比/并列信息用表格或列表，而非长段落
□ 关键判断用 > 引用卡片（每节 ≤ 1 个）
□ 图片独占一段 + 紧跟斜体图注
□ 代码/命令用代码块
□ 步骤类用有序列表，清单类用无序/任务列表

元数据
□ title 简洁（≤12 字）
□ summary 写「读完能带走什么」，40–60 字
□ tags 复用既有词表，2–4 个
□ date 正确，draft: false
□ 无外链失效（如有链接逐个点开验证）

终检
□ 本地 npm run build 通过
□ 详情页首屏无明显排版异常
□ 移动端（窄屏）标题不溢出
```

## 五、润色前后对照（示例）

**润色前**

```
随着 AI 编程工具的普及，token 消耗成了一个不可忽视的问题。我在使用 WorkBuddy 的过程中发现，UI 上只能看到额度，看不到明细，这就导致无法进行成本归因。为了解决这个问题，我开发了一个工具，它可以解析本地日志，然后按任务维度统计 token 消耗，并且支持分档计价。实测发现缓存命中率很高，如果按通用两档计价会高估成本。
```

**润色后**

```
用 AI 干活久了，最说不清的一个问题是：**这笔活到底烧了多少 token、值多少钱**。UI 上只能看到额度，看不到明细，更没法按任务归因。

我做了一个工具来回答它：解析本地请求日志，按任务维度核算消耗，并按真实档位计价。

## 关键发现

实测下来，本机的缓存命中率超过 95%。

| 计价方式 | 结果 |
| -------- | ---- |
| 通用输入/输出两档 | 高估约 70% |
| 分档（非缓存/命中/写入） | 接近真实 |

> 分档计价不是优化项，而是准确性的前提。
```

> 差别不在字数，而在**信息分层**：结论前置、长段拆开、数字进表格、判断进引用。

## 六、发布流程

1. **选文**：你指定本地 md 文件路径（或直接把内容贴给我）
2. **润色**：我按第三节结构规范 + 第四节清单改写，`summary`/`tags` 一并定
3. **入库**：写入 `src/content/articles/zh/<slug>.md`（slug 用英文小写连字符）
4. **验证**：`npm run build` 通过
5. **提交**：你用 GitHub Desktop 提交推送，Netlify 自动上线

> 本轮只出中文版（`lang: zh`）。英文版后续补：在同目录建 `en/<slug>.md`，详情页的语言切换按钮会自动出现。

> 完整流程（含校验脚本、门禁、预览确认）见 [[项目/个人网站编写测试/20-执行/2026-09-30-内容增改管理规范]]。

## 七、SVG 图表规范

> 本节规则来自 2026-09-30 的实战：原有 Mermaid 图表全部改写为内联 SVG。**新图一律用 SVG，不再使用 Mermaid**。

### 7.1 为什么弃用 Mermaid

| 维度 | Mermaid | 内联 SVG |
| ---- | ------- | -------- |
| 渲染时机 | 运行时（CDN 加载后渲染） | 构建时（直接产出静态矢量图） |
| 首屏 | 先空白、后跳动 | 立即呈现 |
| 依赖 | 依赖 `mermaid@11` CDN 可用性 | 零依赖 |
| 样式控制 | 受主题变量限制 | 完全可控，能与站点配色精确对齐 |
| SEO | 文本在 JS 里 | 图内文字进入 HTML |

### 7.2 基本骨架（照抄这个结构）

```html
<div style="margin: 28px 0; overflow-x: auto;">
<svg viewBox="0 0 680 236" width="100%" role="img"
     aria-labelledby="fig1-title fig1-desc"
     xmlns="http://www.w3.org/2000/svg"
     style="font-family: -apple-system, BlinkMacSystemFont, 'PingFang SC', 'Segoe UI', Roboto, sans-serif;">
  <title id="fig1-title">图的名称</title>
  <desc id="fig1-desc">一句话描述这张图表达了什么。</desc>
  <defs>
    <marker id="fig-arrow" viewBox="0 0 10 10" refX="8" refY="5"
            markerWidth="6" markerHeight="6" orient="auto-start-reverse">
      <path d="M2 1L8 5L2 9" fill="none" stroke="context-stroke"
            stroke-width="1.5" stroke-linecap="round" stroke-linejoin="round"/>
    </marker>
  </defs>
  <!-- 图形内容 -->
</svg>
</div>
```

**硬性要求**（缺任一项都会被校验脚本拦截）：

| 项 | 要求 |
| -- | ---- |
| 外层包裹 | `<div style="margin: 28px 0; overflow-x: auto;">` —— 窄屏可横向滚动 |
| 宽度 | `width="100%"`，**不要写死像素宽** |
| `viewBox` | 必须存在；宽度基准统一用 `680` |
| 可访问性 | `role="img"` + `aria-labelledby` 指向 `<title>` 与 `<desc>` 的 id |
| `<title>` / `<desc>` | 必须都有，且 id **全站唯一**（多图时用 `fig1-`、`fig2-` 前缀） |
| 箭头 marker | 定义在 `<defs>` 内；连线的 `<path>` 必须带 `fill="none"` |

### 7.3 配色对齐站点

站点主色来自 `src/styles/global.css` 的 `:root`。SVG 里**必须用十六进制字面量**（CSS 变量在独立 SVG 上下文中不一定继承）。

| 用途 | 色值 |
| ---- | ---- |
| 主强调（蓝）| `#0071e3`，浅底 `#eef4fd` |
| 中性底 | `#f5f5f7`，描边 `#d2d2d7` |
| 正文黑 | `#1d1d1f` |
| 次级灰 | `#6e6e73`，更浅 `#86868b` |
| 警示（橙）| `#c98f00`，浅底 `#fff8e6`，文字 `#96690a` |
| 正向（绿）| `#2f8f5b`，浅底 `#eafaf0` |
| 负向（红）| `#c0392b`，浅底 `#fcebeb` |

**配色纪律**：

- 一张图**最多 2 个强调色**。强调色只给读者最该先看的 1–2 个元素。
- 其余元素一律中性灰。**全图彩色 = 没有重点。**
- 不写内联 `style="color:..."`，颜色统一走 `fill` / `stroke` 属性。

### 7.4 版式纪律

| 项 | 规则 |
| -- | ---- |
| 网格 | 坐标尽量取 4 的倍数，间距对齐不靠目测 |
| 节点数 | 单图**不超过 9 个**；超过就拆成两张 |
| 字号 | 节点标题 13px / 正文 12.5px / 图注 12px；**不小于 11px** |
| 字重 | 只用 400 与 500 两档，**不用 600/700** |
| 圆角 | `rx` 取 10（与站点的 `--radius-md` 呼应） |
| 描边 | 图形边框 `stroke-width="0.5"`，连线 `1.5` |
| 文本居中 | 框内文字加 `text-anchor="middle"` + `dominant-baseline="central"` |
| 文字换行 | SVG **不会自动换行**，长文本必须手动拆成多个 `<text>` |
| 禁止 | 旋转文字、渐变、阴影、发光、emoji、深色底 |

### 7.5 中英双语图的处理

同一张图的中文版与英文版**是两个独立的 SVG**，不是翻译后的替换。

- 英文版 `<title>` / `<desc>` 的 id 加 `-en` 后缀（如 `fig1-title-en`），避免与中文版 id 冲突
- 英文文字更宽，**必须重新核对框宽**：`框宽 ≈ max(标题字数 × 7, 副标题字数 × 6) + 24`
- 英文版节点文字尽量控制在 3 个单词内，超出就精简措辞

### 7.6 SVG 自检清单

```
□ viewBox="0 0 680 …" 存在
□ width="100%"，无固定像素宽
□ role="img" + aria-labelledby 指向的 id 真实存在
□ <title> / <desc> 齐全，id 全站唯一
□ 外层有 overflow-x:auto 包裹
□ 颜色全部用十六进制字面量，强调色 ≤ 2 个
□ 字号 ≥ 11px，字重只用 400/500
□ 连线有 fill="none"
□ 节点 ≤ 9 个
□ 长文本已手动拆行
□ 中英双语版 id 不冲突，英文框宽已重新核对
□ npm run check 通过
```

## 八、项目栏目（projects）排版

> `articles` 与 `practice` 的正文排版规则同样适用于 `projects`。本节只写差异。

### 8.1 三个栏目的定位差异

| | articles | practice | projects |
| -- | -------- | -------- | -------- |
| 页面 | `/articles/` | `/practice/` | `/portfolio/` |
| 排序 | `date` 倒序 | `order` 升序 + 分组 | `order` 升序 |
| meta 行 | `date · tags` | `project_category · work_type · tags` | `year · role · language · ★stars · updated` |
| 语气 | 分享、探讨 | 复盘、结论 | 交付、结果 |

### 8.2 作品详情的推荐结构

沿用现有作品页的写法，按**四段式**组织：

```markdown
开篇一段：这个作品解决什么问题（2–4 句，直接给结论）

## 背景
为什么要做它。让读者理解问题域。

## 我做了什么
核心工作。建议拆成有序列表或小节。

## 关键决策 / 难点
决策点用表格对照（方案 A / 方案 B → 为什么选这个）。
踩过的坑用 callout-warning。

## 结果
用表格给可量化的数据（指标 / 优化前 / 优化后）。
```

### 8.3 差异注意点

| 项 | 说明 |
| -- | ---- |
| **不要手写 `github` / `stars` / `language` / `updated`** | 这 4 个字段由 `sync-github-projects.mjs` 回写，手写会被覆盖，且可能误导 |
| `repo` 是外链开关 | 填了才出现「GitHub 仓库 ↗」；本地项目删掉该行 |
| `summary` 出现在卡片上 | 作品列表是网格卡片，`summary` 太长会撑破版式，**控制在 40 字内** |
| `role` 会显示在详情页 | 写「独立开发」这类简洁表述，不写长句 |
| 图文比例 | 作品页比文章页更需要视觉，**建议至少 1 张图或 1 张表** |

### 8.4 隐私红线（重要）

`personal-site` 是**公开仓库**。作品详情的正文会进入公开源码。

- 涉及第三方平台自动化的项目（如爬虫、自动发布、账号运营类），**不写实现细节**，只写方法论层面
- 未开源项目的描述若要暂缓公开：用 `draft: true` **并且**加入 `.gitignore` —— **草稿不等于保密**，只要文件被提交，描述就已经公开
- 涉及公司、客户、他人信息的，写之前必须确认能否公开

## 九、推送前验证（三步）

> `npm run build` 通过 **≠** 线上正确。本节是本轮实操的直接产物。

### 第一步 · 内容校验

```bash
npm run check
```

拦截 frontmatter 缺失、slug 命名违规、Obsidian 语法残留、双语不一致等问题。
**不通过就不要往下走。** 详见 [[项目/个人网站编写测试/20-执行/2026-09-30-内容增改管理规范]] 第五节。

### 第二步 · 构建

```bash
npm run build
```

> ⚠️ **可能遇到的拦截**：构建末尾报 `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]`，提示无法清理 `dist/pages/` 下的临时文件。
>
> **这通常不是错误**——页面已经生成完毕，只是清理旧产物被沙箱拦下。
>
> 处理方式：
> ```bash
> mv dist "_stale_dist_$(date +%H%M%S)"   # 把旧 dist 改名隔离
> npm run build                            # 重新构建
> ```
> **不要反复重试 `rm`**，会被持续拦截。项目根目录累积的 `_stale_dist_*` 目录可定期手动清理。

### 第三步 · 预览确认

```bash
npm run preview
```

**必须实际打开页面看**，不能只看构建日志。逐项检查：

```
□ 新页面的 URL 可正常访问（非 404）
□ 列表页是否已收录该条目，排序位置是否正确
□ 标题、日期、标签的 meta 行是否正确
□ 表格是否溢出（窄屏）
□ callout 是否渲染为彩色框，而非字面文本
□ SVG 图表是否正常显示、文字有无溢出裁切
□ 站内链接能否正常跳转
□ 移动端窄屏下排版是否可读
```

### 确认之后

```bash
git add src/content
git commit -m "content: 新增 <slug>"
git push
```

> ⚠️ **push 即上线**。Netlify 会在几十秒内自动重建。执行前务必有人工确认。

## 十、图表 vs 表格 vs 列表：该用哪个

内容太多时，容易什么都想画成图。判断标准：

| 想表达 | 用什么 | 理由 |
| ------ | ------ | ---- |
| 流程、时序、状态流转 | **SVG 图** | 有方向和先后关系 |
| 概念之间的包含、依赖 | **SVG 图** | 空间关系比文字更直观 |
| 数值对比、优化前后 | **表格** | 精确数字用表格，不用图 |
| 多个方案权衡 | **表格** | 逐项对照最清晰 |
| 步骤、清单、检查项 | **列表** | 读者要照着做 |
| 趋势、波动 | **SVG 折线图** | 变化趋势需要视觉呈现 |
| 只有 2–3 个并列项 | **正文或列表** | 画成图是过度设计 |

> **先问一句**：读者看这张图，会比读一段好文字学到更多吗？如果不会，就不画。
