# 内容增改管理规范（总纲）

> **本文是内容维护的总入口**，定义「改什么、放哪里、怎么验、什么时候能推」。排版细节见 [[项目/个人网站编写测试/20-执行/2026-09-27-文章润色与排版规范]]，本文不重复。

## 〇、两份规范的分工（先看这个，避免找错文档）

| 你想知道 | 看哪份 |
| -------- | ------ |
| 某个字段是什么意思、放哪个目录 | **本文**（第一、二节） |
| 增改的完整流程、什么时候该停 | **本文**（第三、四节） |
| 脚本怎么用、校验什么 | **本文**（第五节） |
| 标题怎么写才好看、段落怎么分 | 排版规范（第三、四节） |
| 图注怎么写、表格怎么用 | 排版规范（第一节） |
| SVG 图表怎么画 | 排版规范（第七节） |
| 润色前后的对照示例 | 排版规范（第五节） |

一句话：**本文管「工程正确性」，排版规范管「阅读体验」。**

## 一、四类内容集合

站点内容全部位于 `src/content/`，由 `src/content.config.ts` 定义 schema（字段约束）。**新增字段必须先在 schema 里声明，否则构建报错。**

| 集合 | 目录 | 对应页面 | 双语 | 排序依据 |
| ---- | ---- | -------- | ---- | -------- |
| `articles` | `articles/zh\|en/` | `/articles/` | 是 | `date` 倒序 |
| `practice` | `practice/zh\|en/` | `/practice/` | 是 | `order` 升序，按 `project_category` 分组 |
| `projects` | `projects/zh\|en/` | `/portfolio/` | 是 | `order` 升序 |
| `about` | `about/` | `/` 首页 | zh.md + en.md | 固定 |

### 双语的目录约定

- 中文：`zh/<slug>.md`
- 英文：`en/<slug>.md`（**同名**）
- `slug` 用英文小写 + 连字符，如 `ratchet-iteration`
- **文件名（slug）必须与 `lang` 字段一致**：放在 `zh/` 下的文件，`lang` 必须是 `zh`。校验脚本会拦截不匹配。

> 双语不是强制的。只写中文时英文列表页会少一篇，不影响构建。但**一旦补了 `en/`，标题页的语言切换按钮会自动出现**，无需改代码。

### 双语维护原则（2026-10-09 起生效）

**中文版是唯一基准，英文版只做对照翻译并对齐中文版页面。**

这条是硬约定，用于消除中英两版「各写各的」导致的漂移：

| 维度 | 基准 | 英文版做法 |
| ---- | ---- | ---------- |
| 内容 | 中文版正文 | 逐段对照翻译，不增删要点、不改结论 |
| 编排 | 中文版的标题层级与段落顺序 | 严格同构（H2 数量与顺序一致），仅标题文字翻译 |
| 风格 | 中文版的语气、强调方式、列表与引用结构 | 对应还原（加粗、无序列表、末尾 `>` 引用都要保留） |
| 元数据 | 中文版的 `featured` / `order` / `repo` / `cover` / `role` / `year` 等 | 字段值对齐（仅语言相关字段翻译，如 `title` / `summary` / `tags` / `role`） |

执行要点：

- **先改中文，再同步英文**。不先动英文版，避免基准漂移。
- 新增中文条目后，**必须同时补同名的 `en/<slug>.md`**（草稿 `draft: true` 除外），否则英文首页与列表页会少一条，`npm run check` 也会给出警告。
- 英文版只允许「翻译 + 对齐」两种改动，**不允许**自行调整结构、增补观点或删减要点（如确有必要，先在中文版做，再翻译回来）。
- 页面级组件（首页精选区、列表页、详情页）已按 `lang` 取数并复用同一套卡片模板，**补齐内容文件后页面自动对齐，无需改代码**。

> 典型症状：中文首页精选作品有 2 个，英文只剩 1 个 —— 根因几乎总是 `projects/en/` 缺了对应文件，而非模板或过滤逻辑有问题。

## 二、四类内容的字段契约

> 下面是「实际会被渲染出来」的字段。schema 里还有少数预留字段，非必要不使用。

### 2.1 `articles`（文章）

```markdown
---
title: 不许退步的迭代：棘轮机制是怎么工作的   # 列表页 + 详情页标题
lang: zh
date: 2026-08-06
summary: 一句话摘要，显示在卡片上，是点击率的关键
tags: [方法论, 效率, 复盘]
cover: /cover-xxx.png        # 可选，图片放 public/ 下
draft: false                 # true = 不上线
---
```

渲染位置：`title` → 详情页大标题；`date` + `tags` → 标题下方 meta 行；`summary` → 列表卡片。

### 2.2 `practice`（实践经验）

```markdown
---
title: 用 darwin-skill 优化收尾总编 Skill
lang: zh
summary: 一句话摘要
project_category: "工具链开发"        # 列表页按此字段分组，务必与既有分类一致
project_category_en: "Toolchain Development"   # 英文列表页分组名，仅 en 版需要
work_type: "Skill开发"               # 卡片副标题
date: "2026-08-06"
tags: [Skill开发, darwin-skill]
has_diagrams: true                   # 含图表时写 true
order: 3                             # 同组内排序，越小越靠前
status: "published"
draft: false
---
```

渲染位置：meta 行 = `project_category · work_type · tags`。

> ⚠️ `project_category` 是**分组键**，写法不一致会把同一类内容拆成两组。新增分类前先看 `/practice/` 列表页现有哪些组。

### 2.3 `projects`（作品集）

```markdown
---
title: 作品名称
lang: zh
summary: 一句话介绍
tags: [设计, 工具]
repo: JasonWithMiracle/仓库名    # 本地未开源项目：删掉此行
role: 独立开发
year: 2025
demo: https://example.com        # 可选，在线演示
featured: true                   # 首页精选区
order: 1
draft: false

# ⚠️ 以下 4 行由 sync-github-projects.mjs 自动回写，切勿手改
github: "https://github.com/..."
stars: 0
language: "Python"
updated: "2026-09-20"
---
```

**`repo` 字段是唯一开关**：填了才会同步元数据、才出现「GitHub 仓库 ↗」外链按钮；不填则视为本地项目，只显示「查看详情」。

同步命令：`npm run sync:projects`（预演 `npm run sync:projects:dry`）。

### 2.4 `about`（个人简介）

字段：`name` / `role` / `tagline` / `location` / `email` / `lang` / `bio` / `skills[]`。
改动频率低，改完必须同时更新 `zh.md` 与 `en.md`，否则双语页面信息不一致。

### 第 1 步 · 定位

先回答三个问题，再动手：

1. 这篇文章属于哪个集合？（articles 还是 practice）
2. slug 是什么？（英文小写连字符，看下现有文件的命名风格）
3. 是否要双语？

> **articles 与 practice 的区别**：`practice` 是「已落地项目的经验复盘」，带 `project_category` 分组、`order` 排序；`articles` 是「观点、方法、分享」，按时间倒序。同一件事可以两边都放，但**必须写成不同版本**（practice 偏技术细节，articles 偏可读性），不能复制粘贴。

### 第 2 步 · 撰写

按第二节对应集合的字段契约填写 frontmatter，正文按排版规范写。

### 第 3 步 · 校验

```bash
npm run check          # 全量校验
npm run check -- --grep darwin    # 只校验文件名含 darwin 的条目
```

校验项见第五节。**不通过就不要往下走。**

### 第 4 步 · 构建与预览

```bash
npm run build
npm run preview
```

必须实际打开详情页看效果，重点检查：SVG 是否正常渲染、callout 是否变彩色框（而不是字面文本）、表格是否溢出、移动端窄屏是否挤爆。

### 第 5 步 · 推送

```bash
git add src/content
git commit -m "content: 新增 <slug>"
git push
```

> ⚠️ **推送即上线**：`personal-site` 仓库与 Netlify 连通，push 后自动重建。执行前必须有明确的人工确认。
>
> 若推送前需要更保险，可先 `git push` 到分支，本地 `npm run preview` 复核后再合入 main。

## 四、四个必须停下来确认的门禁

前三个流程问题都是「可以自动化」的，但下面四件事**必须人工拍板**：

| # | 门禁 | 为什么不能自动 |
| - | ---- | -------------- |
| 1 | **是否公开** | VoiceDesk 等项目的描述可能涉及未开源内容；`personal-site` 是公开仓库，**一旦提交，项目描述就进了公开源码**，即使页面不渲染 |
| 2 | **内容准确性** | 数字、结论、项目名一旦写错，上线即是公开的错误 |
| 3 | **署名与隐私** | 涉及他人、公司、客户的信息必须确认能否公开 |
| 4 | **推送上线** | 触发线上变更，不可回退到「用户没看见」的状态 |

> 第 1 条有实战教训：曾有一次 VoiceDesk 以 `draft: true` 备妥，页面不渲染，但**文件本身若提交进公开仓库，描述即已泄露**。最终是通过加入 `.gitignore` 规避。**草稿 ≠ 保密。**

## 五、校验脚本

### 5.1 用法

```bash
npm run check              # 校验全部内容
npm run check -- --grep X  # 只校验匹配 X 的条目
npm run check -- --json    # 输出 JSON，便于接入其它工具
```

### 5.2 校验项

| 类别 | 检查内容 | 级别 |
| ---- | -------- | ---- |
| frontmatter | 必填字段是否存在、类型是否正确 | 错误 |
| frontmatter | `lang` 与所在目录（`zh`/`en`）是否一致 | 错误 |
| frontmatter | `draft` 是否为布尔值 | 错误 |
| frontmatter | `date` 格式是否可解析 | 错误 |
| 命名 | slug 是否为小写英文 + 连字符（无中文、无空格、无大写） | 错误 |
| 双语 | 中文条目是否存在（不要求反向必须存在） | 提示 |
| 渲染 | 是否残留 Obsidian 语法（`> [!tip]`、`[[wikilink]]`、`![[embed]]`） | 错误 |
| 链接 | 站内绝对链接指向的页面是否真实存在 | 警告 |
| 图片 | `cover` / 正文图片引用的文件是否存在于 `public/` | 警告 |
| 图表 | `has_diagrams: true` 但正文无 `<svg>` 或图片 | 警告 |

**错误** 必须修复；**警告** 需人工判断（例如站内链接指向尚未创建但即将创建的页面）。

### 5.3 为什么需要它

本轮实操中出现的两类问题，都是「肉眼看不出来」的：

1. `> [!tip]` 手写后**构建成功但渲染成字面文本** —— build 不报错，只有打开页面才发现。
2. `sync:projects` 的 `repo` 字段拼写错误 —— 不报错，只是外链静默消失。

这两类问题的共同特征是**静默失败**。构建通过 ≠ 内容正确，所以需要一道独立于构建的检查。

## 六、常见场景速查

| 场景 | 操作 |
| ---- | ---- |
| 新增一篇文章 | 见第三节完整流程；文件放 `articles/zh/<slug>.md` |
| 给已有文章补英文版 | 在 `articles/en/` 建**同名**文件，`lang: en` |
| 中文有、英文少一条（页面数量不一致） | 对照中文 `zh/<slug>.md` 补 `en/<slug>.md`：字段对齐、正文逐段对照翻译（见第一节「双语维护原则」） |
| 修改已有内容 | **先改中文版**，再按「翻译 + 对齐」同步英文版；两版标题层级与段落结构必须同构 |
| 新增一件作品（已开源） | `projects/zh/<slug>.md`，填 `repo`，跑 `npm run sync:projects` |
| 新增一件作品（本地） | `projects/zh/<slug>.md`，**不填** `repo` |
| 把草稿转正式 | `draft: false`，重新校验 + 构建 + 预览 |
| 下线一篇内容 | 优先 `draft: true`（保留内容）；确需删除则同时删 `zh` 与 `en` |
| 改标题/摘要 | 直接改 frontmatter，无需动正文 |
| 调整排序 | 改 `order`（practice / projects）；articles 改 `date` |
| 新增内容分类 | 改 `src/content.config.ts` 的 schema，**并在 `/practice/` 列表页确认新分组名** |

## 七、维护约定

- 本文与排版规范**同时更新**：改字段契约 → 本文；改排版规则 → 排版规范。
- 每次因「违反本规范」而返工后，把该场景补进第六节速查表 —— 规范的完整性靠实战补充，不靠一次写全。
- 校验脚本的检查项应对齐 5.2 表格；新增检查项时同步更新表格。
